# Incremental Implementation

Порядок по умолчанию:

1. Сначала прочитай соседние файлы.
2. Сделай наименьшее полезное изменение.
3. Если меняется контракт, обнови всех вызывающих.
4. Запусти наименьшую проверку, доказывающую, что затронутая поверхность работает.
5. Остановись до несвязанных рефакторингов.

Frontend:

- сохраняй существующую форму состояния и API-хелперы;
- держи изменения UX в рамках запрошенного пути;
- проверка типов и узкие тесты (если тесты разрешены владельцем проекта); для изменённых UI-флоу пройди сценарий приёмки вручную на тестовом стенде и сними ключевые этапы; для видимых изменений вёрстки проверь десктоп и мобильную ширину;
- тесты — часть шага, а не последующая задача (если тесты разрешены владельцем проекта): поведение изменилось → тест переписан в том же шаге, функция добавлена → тест добавлен, функция удалена → тест удалён (коммит это сообщает). Никогда не пропускай и не ослабляй тест ради зелёного результата.

Backend:

- изменения схемы — вместе с миграциями;
- держи общие стоимости и контракты согласованными между вызывающими поверхностями;
- скомпилируй или импортируй изменённые модули и запусти самый узкий релевантный набор тестов (если тесты разрешены владельцем проекта).

Документация и скрипты:

- для исполняемых скриптов — проверка синтаксиса, справки или парсера;
- после переименований поищи устаревшие имена, пути и ссылки на контракты.

Субагенты проверяют свои куски. Главная сессия повторяет итоговую узкую проверку после интеграции. Сбой, вызванный текущим изменением, остаётся частью той же задачи: исправь, повтори упавшую проверку, затем отчитайся. Не жди нового запроса.
