# Frontend UI Engineering

Первый справочник по интерфейсу проекта (адрес стенда, вход, готовые компоненты, дизайн-система - `project.md`).

Правила:

- перед видимой правкой - дизайн-система проекта (`project.md`): токены темы, готовые компоненты и классы;
- совпадать с существующими паттернами интерфейса, прежде чем придумывать новые;
- тексты простые, для нетехнических пользователей;
- не обещать в текстах то, чего продукт сейчас не поддерживает;
- без маркетингового пафоса на рабочих экранах;
- контролы предсказуемые: вкладки для режимов, переключатели для бинарного выбора, поля/слайдеры для чисел;
- компактные макеты для экранов приложения, богатая визуализация - только на лендинге;
- проверять мобильную и десктопную версии на наложения, переполнение и выравнивание;
- **любая модалка/оверлей ОБЯЗАНА закрываться крестиком, кликом по фону и Esc ВСЕГДА** - независимо от загрузки/операции/`disabled`/`busy`. Не гейтить пути закрытия под `busy` (фоновая работа продолжится). Проверять явно на модалках основных флоу;
- **многозадачный запрос** (несколько багов/правок в одном сообщении) - перечислить все подзадачи пунктами и отметить каждую как сделана/проверена перед «готово», чтобы ни одна не потерялась.
- если точная цена до запуска неизвестна - показывать диапазон.

## Стандарт окна и экрана

Обязателен для любого нового окна, панели и списка; при правке существующего - для того, что трогаешь.

**Перед кодом коротко, не документ:**

1. что пользователь делает по шагам и что видит («жмёт «Переименовать» → видит поле и кнопку «Сохранить»»), 3-5 шагов;
2. какие из четырёх состояний затронуты.

**Четыре состояния. Окно без них не готово** - большинство «нерабочих кусков» это ненаписанные три:

| Состояние | Что должно быть видно |
|---|---|
| Пусто | текст, почему пусто, и действие, которое это исправит - не белое пятно |
| Грузится | скелет или индикатор на месте будущего содержимого; кнопка действия заблокирована, но окно закрывается |
| Ошибка | причина словами пользователя + что сделать; остаётся в окне, пока не ушли |
| Получилось | видимое подтверждение: новое содержимое, тост или закрытие окна |

**Правила корпуса:**

- собирать из готового корпуса окна проекта (см. `project.md`), а не с нуля: он уже
  держит крестик, Esc, клик по фону, замок фокуса, прокрутку тела и ряд кнопок. Новое окно, написанное
  мимо него, - повод вернуть задачу;
- **закрытие работает ВСЕГДА** - крестик, фон и Esc, независимо от загрузки, операции и `disabled`
  (фоновая работа продолжится);
- ошибка живёт В окне, а не мелькающим тостом: пользователь должен успеть прочитать причину;
- главное действие - справа, отмена - слева; необратимое действие спрашивает подтверждение;
- размеры, отступы и цвета - только токенами темы (`var(--...)`). Хардкод rgba «под тёмную» ломает
  светлую: швы и невидимые карточки;
- тексты - простым языком пользователя, без внутренних терминов продукта (см. `ui-principles`);
- ширины - из `project.md`.

## Дизайн-проход экрана

Когда экран нужно выровнять целиком, а не поправить одно место. Сначала диагноз по скринам живого экрана, потом правки,
потом скрины «после». Вслепую не править.

1. **Скрин «до»** на всех ширинах из `project.md` (узкая ломается чаще); если в проекте есть скрипт поиска переполнений
   (обрезанный текст, горизонтальный скролл, таблицы за краем) - прогнать его.
2. **Диагноз** словами пользователя («подпись обрезана», «непонятно, где переключатель»), 3-7 пунктов.
3. **Правки** - токенами темы, в обеих темах; окна закрываются крестиком, фоном и Esc.
4. **Скрин «после»** и повторный поиск переполнений: правка часто ломает соседнее.
5. Скрины владельцу - в папку скринов из `project.md`, по одному блоку на скрин, имена с номерами и `-до`/`-после`.

Не менять размеры карточек и превью без просьбы, не добавлять библиотеки, шрифты и зависимости без «да» владельца, не
полировать бесконечно: пачка правок, одна проверка, стоп.

Лендинг, если есть:

- Не добавлять новые UI/motion-библиотеки - хватает существующего стека и готовых компонентов.
- Цены и лимиты - единый источник истины, совпадающий с сервером. Не держать дубли в разметке; цену выбирает сервер.
- Числа, встречающиеся и в тексте, и в анимации, брать из одной константы.
- Копирайт лендинга - тон и обращение по правилам проекта (`project.md`), без внутренних терминов.
- Порядок работы: сначала весь визуал одним проходом, потом отдельным проходом тексты - не смешивать.
- Адаптив проверять на всех ширинах из `project.md`: без обрезки текста, наложений и горизонтального скролла.

## Визуальная проверка - по тому, что изменилось

Правило одно:

- **изменилось поведение или флоу** (новое окно, новый шаг, другая логика кнопки, другой набор
  состояний) → перед словом «готово» пройти сценарий приёмки из плана (3-5 шагов «делает X → видит Y») браузером на
  тестовом стенде под служебным аккаунтом, на готовых данных, без новых платных генераций, и снять скрины КАЖДОГО
  затронутого состояния из четырёх в папку скринов из `project.md`. Состояния нет в готовых данных - спек с моками,
  скилл `frontend-e2e`. Расхождение со сценарием - чинить в той же задаче. Зелёная проверка типов этого НЕ заменяет: он не знает, что окно не закрывается и что при
  пустом списке видно белое пятно;
- **чисто текстовая или косметическая правка** без изменения поведения → хватает проверки типов.

Скриншот сверх этого - инструмент под рукой: снимай, когда сам хочешь убедиться глазами в
структурной вёрстке (мог схлопнуться блок, поехать сетка).

Метод:
- Публичные страницы - headless Chrome по адресу тестового стенда:
  `chrome --headless=new --disable-gpu --hide-scrollbars --window-size=1440,900 --screenshot=<out.png> "<адрес стенда>?v=<ts>"` → затем Read PNG.
- Авторизованные страницы - `tools/screenshot.py` (вход под служебным тестовым аккаунтом; адрес - только из `BASE_URL`, данные входа - из окружения, см. `project.md`).
- Проверять и desktop, и узкие ширины (ширины из `project.md`). Если правка визуальная - сравнить «до/после».
- Идеально проверять ДО выката на стенд; если инфраструктуры нет - выкат на стенд и сразу скриншот, при дефекте чинить и выкатить заново.
