# Code Review And Quality

Порядок ревью:

1. Регрессии поведения.
2. Риски авторизации, денег и безопасности.
3. Нарушенные контракты API и схем.
4. Не обновлённые вызывающие места и миграции.
5. Регрессии интерфейса.

Перед подтверждением:

- запусти наименьшую практичную проверку — «наименьшая» значит узкая по охвату, но не слабее по строгости;
- проверка, которую не удалось выполнить, — непроверенная область: назови её и скажи, что остаётся недоказанным. Не выдавай её за пройденную;
- упавшая проверка не объявляется флейком без доказательства (повтор, изоляция, ссылка на причину);
- убедись, что тесты изменились вместе с кодом (если тесты в задаче разрешены владельцем проекта): поведение изменилось → тест переписан, функция добавлена → тест добавлен, функция удалена → тест удалён. Зелёный прогон, достигнутый удалением, ослаблением или пропуском теста, — блокер ревью;
- для изменённого UI-флоу в доказательствах должен быть ручной проход сценария приёмки на тестовом стенде и снимки ключевых этапов — одна зелёная проверка типов флоу не подтверждает;
- если тесты разрешены: исправление бага на стыке без теста стыка, либо мок, расширенный до «принимает что угодно», — блокер ревью;
- крупная функция (новый экран/флоу): приёмку делает свежий субагент, который видит только формулировку задачи и сценарий приёмки — не diff и не реализацию.
